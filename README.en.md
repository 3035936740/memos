# Memos Plus

**A self-hosted blog, Markdown notebook, and home for small communities—with a look of your own.**

Memos Plus is an independently maintained, unofficial derivative of [Memos](https://github.com/usememos/memos), with its own versioning and release schedule. The original copyright and MIT license notices are retained. We thank the upstream authors and contributors. This project is not an official Memos release and is not endorsed by upstream.

## What it adds

Memos Plus keeps Memos's quick Markdown capture and self-hosted data ownership, while adding blogging, customization, and shared Spaces:

- **Blog 2 and ten built-in styles:** Default, Glass, Neumorphism, Frutiger Aero, Y2K, Vaporwave, Pixel Retro, Hand-drawn, Developer, and the unlockable Golden style. Styles extend to navigation, the editor, settings, and dialogs.
- **Styles that react to color themes:** More than twenty color themes combine with styles to create particles and scenes, ten legendary combinations, a codex, and achievements.
- **Reading tools:** Reading progress, estimated reading time, series navigation, old-post reminders, resume reading, and a sticky sidebar.
- **Per-post appearance:** `#style/...` and `#theme/...` tags select a post's style and colors, with an override for readers who prefer their own choices.
- **Today on Home:** Writing streaks, posts from this day in earlier years, notifications, and a daily question shared by the site. “Write an answer” includes the question and the day's tag. The site's seed determines the schedule; a custom bank with fewer than 365 questions repeats only after each shuffled round is exhausted.
- **Background music:** An administrator-managed playlist with uploads or URLs, volume controls, playback order, and style-specific visualization.
- **Styled share images:** Post images use the current style and colors, with the site name and address.
- **Spaces:** Small communities with their own `/space/<UID-or-alias>` address, name, avatar, and public, signed-in-only, or invitation-only access. Larger directories support search, sorting, and random discovery.
- **Safer writing:** A pre-publication privacy check, trash, private revision history, batch actions, and quick navigation with Ctrl/⌘ + K.
- **Administration:** First-sign-in setup, shareable appearance presets, installable CSS style packs, site backup exports, and optional AI text/image moderation. AI moderation switches default to off.
- **Blog import:** Preview and import WordPress exports or Markdown ZIP archives, retaining supported dates and metadata.

The demo link above is the maintainer-provided deployment, not an uptime or compatibility guarantee.

## Get started

### Choose an installation method

The workflows configure these container tags under `ghcr.io/3035936740/memos-plus`:

| Tag | Intended use |
| --- | --- |
| `latest`, major/minor tags such as `1.0`, exact release version | Successful non-prerelease tag builds; pin an actual published version for predictable upgrades. |
| Exact `1.x.y-rc.N` version | Prerelease tag builds; not promoted to `latest`. |
| `canary` | Successful builds of `main`; may contain unreleased changes. |

The presence of a workflow does **not** mean a particular tag is available or anonymously pullable. Check [Actions](https://github.com/3035936740/memos-plus/actions) and the [release assets](https://github.com/3035936740/memos-plus/releases) before choosing a download. Historical releases may contain only directly downloadable Windows/Linux binaries, not the archive names generated by the current workflow. If a container tag is unavailable, [build from source](#build-from-source); do not substitute the upstream Memos image.

### Docker

With an available image:

```bash
docker run -d \
  --name memos-plus \
  --restart unless-stopped \
  -p 5230:5230 \
  -v "$HOME/.memos-plus:/var/opt/memos" \
  ghcr.io/3035936740/memos-plus:latest
```

Open `http://localhost:5230`, or `http://YOUR_SERVER:5230` from another computer. The first account created on a fresh instance is the administrator; sign in to complete the setup wizard. Expose a public deployment through a properly configured HTTPS reverse proxy and review registration and access settings.

The container listens on **5230** because its Dockerfile sets `MEMOS_PORT=5230`. Native binaries and `go run` default to **8081**; the examples below explicitly choose a port. The data mount must survive container replacement. An unmounted container is not a backup.

### Docker Compose

The maintained deployment example is [deploy/docker-compose.yml](deploy/docker-compose.yml):

```bash
mkdir memos-plus && cd memos-plus
curl -fLO https://raw.githubusercontent.com/3035936740/memos-plus/main/deploy/docker-compose.yml
docker compose up -d
docker compose logs --tail=100 memos-plus
```

It exposes `5230:5230` and mounts `./data:/var/opt/memos`. Here `./data` is next to the downloaded Compose file. If you instead run `docker compose -f deploy/docker-compose.yml up -d` from a checkout, its relative mount is **`deploy/data`**, not the checkout's root `data` directory. Keep the deployment directory and its configuration together.

For 1Panel, BaoTa, or another container panel, use its Compose editor and this same file. Check how the panel resolves relative bind-mount paths. A separately built local image can be used by changing the service's `image` to `memos-plus:local`; build it first with the commands below. The alternate [scripts/compose.yaml](scripts/compose.yaml) also uses Plus, but retains the `memos` service/container name and mounts `~/.memos-plus/`. Do not switch examples without explicitly mapping your existing data directory.

### Native binaries

Download a binary or archive for your OS and architecture from [this project's Releases](https://github.com/3035936740/memos-plus/releases). The current release workflow targets Linux amd64/arm64/armv7, macOS amd64/arm64, and Windows amd64. This is a build matrix, not a promise that all assets exist in historical releases.

Current workflow archives are named `memos-plus_<version>_<os>_<arch>.tar.gz`, or `.zip` on Windows; ARM v7 uses `armv7`. They contain `memos` or `memos.exe` at the archive root. If a historical release provides a raw file such as `memos-linux-amd64` or `memos-windows-x64.exe`, rename it to `memos` or `memos.exe` to follow these examples. Verify `checksums.txt` when the release provides it.

Linux/macOS:

```bash
chmod +x ./memos
./memos --port 5230 --data ./data
```

Windows PowerShell:

```powershell
.\memos.exe --port 5230 --data .\data
```

The data directory is created when needed. Relative paths resolve from the **working directory**, not the executable's location. Use an absolute path in a service definition, configure your process supervisor to restart the binary, and keep the same data path across upgrades.

### Configuration and persistence

Command-line flags also have `MEMOS_` environment equivalents; hyphens become underscores. Flags take precedence over their environment equivalents.

| Flag / environment variable | Meaning |
| --- | --- |
| `--port` / `MEMOS_PORT` | Listening port: native default `8081`, container default `5230`. |
| `--addr` / `MEMOS_ADDR` | Bind address; `127.0.0.1` limits native access to the local machine. |
| `--data` / `MEMOS_DATA` | Persistent data directory. Container deployments mount `/var/opt/memos`; specify a path explicitly for native services. |
| `--driver` / `MEMOS_DRIVER` | Database driver: `sqlite` (default), `mysql`, or `postgres`. External databases need provisioning and backups of their own. |
| `--dsn` / `MEMOS_DSN` | Database connection string; empty with SQLite uses `memos_prod.db` under the data directory. The container entrypoint also accepts `MEMOS_DSN_FILE` for a readable secret file; do not set both. |
| `--instance-url` / `MEMOS_INSTANCE_URL` | Canonical external HTTP/HTTPS site URL, for example `https://notes.example.com`. Set it correctly behind a reverse proxy. |
| `--demo` / `MEMOS_DEMO` | **Destructive demo mode**, off by default. Only use with disposable, isolated SQLite data. |
| `TZ` | Container timezone; defaults to `UTC`. |
| `MEMOS_UID`, `MEMOS_GID` | Container runtime identity; both default to `10001`. The root entrypoint fixes volume ownership before dropping privileges. |

Do not change driver or DSN expecting automatic transfer between database engines. Keep local uploads, public storage files, and any externally configured S3/object storage in your backup plan. File-backed deployment settings and identity providers are documented in [Configuration Provisioning](docs/configuration-provisioning.md); keep copies of deployment secrets outside the application export.

For a small server, SQLite and the Default first-visit style are reasonable starting choices. A 1-core/1-GB deployment has not been established here as a tested minimum specification. Visual effects also depend on the visitor's device.

## Give a post its own appearance

Include either or both tags in a post:

```markdown
#style/vaporwave #theme/neon-rain
```

The selection applies while reading that post. Leaving it restores the reader's preferences rather than overwriting them. A notice lets readers use their own appearance; manually choosing another style or color theme also overrides the post.

- Styles apply only in **Blog 2**. Color themes apply in any layout.
- Names are case-insensitive. Invalid names are ignored; the first tag of each kind wins.
- Golden must be unlocked by the reader and cannot be forced with a tag.
- Enabled community styles can be selected with `#style/<pack-ID>`.

## Import from another blog

Open **Settings → Spaces**, then open a Space you administer and select its **Import** tab. Only Space administrators can import there. Instance administrators also have a **Main site import** entry on the Spaces settings page. There is no separate top-level Import settings item.

1. Enter a consistent source-blog name or address and choose an export:
   - WordPress `.xml` (WXR).
   - A `.zip` containing Markdown `.md` files, such as Hexo, Hugo, or Jekyll posts. YAML and TOML front matter are supported.
   - For Typecho or another platform, first export to WordPress format using an appropriate exporter.
2. Preview and select posts, check their target Space/site, and choose visibility. The import defaults to private.
3. Confirm the import. It can be cancelled; the result lists imported, skipped, and failed items.

Supported publication dates, draft status, tags, and categories are retained. Images included in Markdown ZIPs are uploaded; external images retain their URLs and are not fetched by the server. Using the same source identifier on a later import lets the importer skip already imported posts. Blocked-word and enabled AI moderation also apply. The instance administrator can adjust the import upload limit in the import screen; the default is **100 MiB**.

This is a **content importer**, not a full database or backup-restoration tool. Do not assume that users, credentials, comments, or every platform-specific feature will migrate with a blog export.

## Community style packs

Administrators can install additional styles under **Settings → Style packs**:

- A pack is a ZIP containing `style.json` and `style.css`, with optional images and fonts. Repository [examples](example/stylepacks/) and the [authoring guide](docs/style-pack-authoring.md) are available; the detailed authoring/API guides are currently in Chinese.
- New packs are disabled until an administrator enables them. Enabled packs are offered to visitors and support `#style/<pack-ID>`.
- A pack can reuse a built-in style's color-reaction rules or opt out of reactions.
- Packs may not contain scripts or load external resources. The server validates the archive and CSS.
- Disabling or deleting a pack makes its users, first-visit defaults, and affected posts fall back to Default.

An **appearance preset** that shares site appearance settings is distinct from a CSS style-pack ZIP; the formats are not interchangeable.

## Backups, upgrades, and recovery

- **Site export:** An instance administrator can download a backup ZIP under **Settings → Storage**. It contains readable Markdown, metadata, and included attachments. Review its manifest for skipped or failed attachment exports. It is not, by default, a complete restorable database backup.
- **SQLite snapshot:** The export offers an optional database snapshot. It contains password hashes and keys: protect the archive as a secret. For MySQL/PostgreSQL, use the database's native backup tools separately.
- **Trash:** Deleted posts go to **user menu → Trash**. Retention defaults to 30 days; posts may be restored or permanently deleted.
- **History:** Changes to content/title retain private revisions; consecutive edits by one person within ten minutes are grouped. The default limit is 20 revisions per post. Authorized post managers can compare and restore revisions from the post menu.
- Retention and history limits are configurable in **Settings → System → Advanced**.

Before upgrading, record the current version/image tag and deployment configuration, stop writes, and back up the complete data directory plus the database and external storage. Test the new version on an isolated copy first. Never point the test instance at the production database, upload directory, or object-storage write target.

For Compose, after making a restorable backup, select a published tag in the Compose file and run:

```bash
docker compose pull
docker compose up -d
docker compose logs --tail=100 memos-plus
```

For native deployments, stop the old process, replace the executable, and start it with the same data path and database configuration. Startup may migrate the database. Simply reverting the executable or container tag does **not** undo a schema upgrade.

To roll back, stop the new instance and restore the **pre-upgrade** database, local data directory, deployment configuration, and external objects as a consistent set, then start the matching old version. With a stopped SQLite instance, restoring a cold copy of the complete data directory is the simplest approach; do not mix a restored database with WAL/SHM files from a different database state. MySQL/PostgreSQL require a matching database restore as well. A Markdown-only export cannot restore accounts, credentials, settings, and database schema.

## Migrating from upstream Memos

This project retains the upstream Go module, database drivers, data-directory conventions, and protocol namespaces. It also adds Plus-specific tables and fields and an independent migration ledger.

The current source's upstream schema target is **`0.34.1`**, recorded in [internal/version/upstream-version.txt](internal/version/upstream-version.txt). This is not the Plus release number or a claim of universal migration compatibility. The server rejects databases newer than its target. Its legacy guard directs installations older than `0.22.0` through upstream `0.25.x` first. Other versions and customized databases still require a trial migration on a disposable copy.

1. Stop the upstream instance and make a complete, restorable backup: data directory, actual database (including an external DB if used), uploads/object storage, and configuration.
2. Start the chosen Plus build against an **isolated copy** with the same database driver and compatible connection settings. Check its logs and inspect users, posts, permissions, Spaces, attachments, and a new create/edit operation.
3. Only schedule the production cutover after that trial succeeds for your actual source version. Keep the upstream instance stopped during cutover and avoid concurrent writers.

For an initialized SQLite database that needs migration, the code takes a pre-upgrade snapshot in the data directory and retains the three most recent `memos_prod.db.before-*.bak` snapshots. Snapshot failure stops migration. This protects the database only, not external files, and does not replace your own backup. MySQL/PostgreSQL do not receive automatic snapshots.

**Do not reopen the upgraded database with upstream Memos.** Returning to upstream requires the pre-migration backup and matching upstream executable. Plus uses its own `1.x` release version and migration ledger while preserving the upstream schema version; About displays both. CI includes upgrade checks, but neither their existence nor this README proves that your source version/database has passed them.

## Build from source

Requirements are pinned by the repository: **Go 1.26.2**, **Node.js 24 or newer**, and **pnpm 11.0.1**. Node 24 is used by CI. Use the existing lockfile; do not switch package managers.

```bash
git clone https://github.com/3035936740/memos-plus.git
cd memos-plus
npm install -g pnpm@11.0.1
pnpm --dir web install --frozen-lockfile
pnpm --dir web release
```

Build the frontend **before** the backend: Go embeds `server/router/frontend/dist`, and the Dockerfile does not build the frontend itself.

Linux/macOS shell:

```bash
CGO_ENABLED=0 go build -trimpath -o memos ./cmd/memos
./memos --port 5230 --data ./data
```

Windows PowerShell:

```powershell
$env:CGO_ENABLED = "0"
go build -trimpath -o memos.exe ./cmd/memos
.\memos.exe --port 5230 --data .\data
```

To build your own container from the repository root after `pnpm --dir web release`:

```bash
docker build -f scripts/Dockerfile -t memos-plus:local .
docker run -d --name memos-plus --restart unless-stopped \
  -p 5230:5230 -v "$HOME/.memos-plus:/var/opt/memos" memos-plus:local
```

Windows batch helpers also exist: `build-windows.bat` writes `bin/memos.exe`, and `build-linux-amd64.bat` cross-compiles to `bin/memos-linux-amd64`. They install dependencies, build the frontend, and remove explicitly named legacy frontend files; use a backed-up checkout. The explicit commands above avoid that cleanup. The Linux cross-build runs with `chmod +x ./memos-linux-amd64` followed by `./memos-linux-amd64 --port 5230 --data ./data`.

### Development and checks

Use separate terminals and a dedicated development data directory:

```bash
go run ./cmd/memos --addr 127.0.0.1 --port 8081 --data ./dev-data
```

```bash
cd web
pnpm dev
```

Vite serves `http://localhost:3001` and proxies the configured API/file paths to `http://localhost:8081`; `DEV_PROXY_SERVER` changes that backend target. Use the backend-served, embedded build when checking server-generated initial branding or the dynamic Web App manifest.

The project's existing checks include:

```bash
pnpm --dir web lint
pnpm --dir web test
pnpm --dir web release
DRIVER=sqlite go test ./...
```

The last command is POSIX shell syntax; in PowerShell set `$env:DRIVER = "sqlite"` before `go test ./...`. MySQL/PostgreSQL store tests and `scripts/release_smoke_test.sh` require their configured database/container environment. The release smoke script uses Docker, defaults its upstream image to the schema target file, and accepts `--previous-image` for an explicit source image. These commands describe how to check a change; they are not a record of tests already passed.

## Disposable demo mode

The maintainer's linked demo is a regular deployment. To create an explicitly disposable playground, use [deploy/docker-compose.demo.yml](deploy/docker-compose.demo.yml):

```bash
docker compose -f deploy/docker-compose.demo.yml up -d
```

This example uses `canary`, binds **`127.0.0.1:5231`**, and stores data in a separate named volume. `MEMOS_DEMO=true` resets demo data **at startup and every 24 hours**. Demo mode supports SQLite only. Never use production data or a production DSN, never store private information there, and do not mistake normal deployment for reset-enabled demo mode. See [demo deployment notes](deploy/demo.md) for the current restrictions and reset behavior.
